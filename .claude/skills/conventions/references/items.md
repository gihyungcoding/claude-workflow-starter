# 항목 카탈로그 — 코드 없이 정할 수 있는 것, 그리고 왜 지금인가

각 항목: **질문** · **왜 지금**(나중에 정했을 때의 실제 비용 — ticket-booking 시험 실행) · **분류**(`decision-protocol.md`) · **검사 수단**.
추천 기본값은 `stacks/<스택>.md` 에 있다. 스택 파일에 없는 스택은 질문만 하고 추천값 없이 정한다.

---

## C-TESTDB — 테스트는 어느 DB 로 도는가
- **질문**: 운영 DB 와 같은 종류로 테스트하나? (Testcontainers·Docker)
- **왜 지금**: 운영 PostgreSQL, 테스트 H2 로 시작하고 "DB 전용 기능을 쓰는 순간 전환"하기로 했지만 두 달 동안 전환하지 않았다.
  PostgreSQL 에서만 나는 입력 버그로 Phase 4 FAIL 4회(TASK-009), 전환 직후 거짓 실패 10건(TASK-012). 전환 조건을 적어도 지켜지지 않았다.
- **분류**: 운영 DB 가 정해져 있고 Docker 를 쓸 수 있으면 `mechanical`(같은 DB). Docker 를 못 쓰면 `user_challenge`.
- **검사**: 게이트 — 운영과 다르면 ADR + `promote_after: TASK-…` 가 없으면 불통과.

## C-LINT — 포매터·린터·엄격도
- **질문**: 포매터와 린터는 무엇이고 엄격도(TS `strict`, 경고를 오류로)는?
- **왜 지금**: 첫 태스크의 Red 이후에 포매터를 넣어 15개 파일이 한 번에 재정렬됐다. 프론트는 첫 Red 커밋 안에서 린터를 골랐고 TS `strict` 는 끝내 명시하지 않았다.
- **분류**: 스택 기본값이 있으면 `mechanical`. 팀 취향이 갈리면 `taste`.
- **검사**: 게이트 — `CLAUDE.md` 린트 명령이 TODO 가 아니고 설정 파일이 있다. Phase 3·4 에서 설정 파일은 훅이 보호한다.

## C-LAYOUT — 패키지·폴더 배치, DTO 는 어디에
- **질문**: 계층별 폴더 이름(`api/`·`service/`·`repository/` …), 요청·응답 DTO 의 위치, 프론트 폴더.
- **왜 지금**: 응답 DTO 위치를 정하지 않아 첫 태스크 계획이 기존 제약(서비스→api 의존 금지)을 어겼다 → 두 번째 PR·9개 파일 리팩터링, 지금도 어긋난 파일이 남았다.
  빈 저장소에서 쓴 제약 경로(`**/controller/**`)가 실제 패키지(`**/api/**`)와 달라 검사가 계속 거짓 통과했다.
- **분류**: `architecture.md` 계층이 정했으면 `mechanical`, 이름은 `taste`.
- **검사**: 제약(`forbidden_import`·`required_path`) — **빈 저장소라 `error` 로 시작**. 경로가 실제 파일과 맞는지는 4.5 기준 구현 뒤 `no_target` 0 으로 확인.

## C-ERROR — 에러 응답 형식과 예외 처리 위치
- **질문**: API 에러 본문 모양(예: `{code, message, details?}`), 에러 코드 이름 규칙, 예외를 어디서 응답으로 바꾸나(전역 핸들러 하나 / 도메인별).
- **왜 지금**: 첫 태스크가 `{code, message}` 를 암묵적으로 만들고 문서에 적지 않았다. 이후 값 크기에 따라 코드가 달라지고, 전역 핸들러가 필드 이름 문자열로 분기했다.
- **분류**: `taste`(모양) + `mechanical`(스택 관례).
- **검사**: 리뷰 + 기준 구현의 에러 테스트. 가능하면 제약(예: 컨트롤러에서 직접 `ResponseEntity.status(…)` 금지).

## C-VALID — 입력 검증 방식
- **질문**: 선언형 검증(Bean Validation·zod·pydantic)을 쓰나, 어느 층에서 하나?
- **왜 지금**: 라이브러리가 의존성에 있는데 아무도 쓰기로 정하지 않아 서비스에서 손으로 검증했다 → ADR 로 바꾸고 이전 전용 태스크(14개 파일) + 분리된 수정 태스크.
- **분류**: 스택 기본값이 있으면 `mechanical`.
- **함께 정할 것 — 숫자·식별자 입력은 ASCII 범위로**: 언어의 "숫자" 판정은 유니코드 숫자도 받는다(Python `isdigit()`·`\d`, Java `Character.isDigit`).
  겉모습이 다른 값이 정규화·중복 검사를 빠져나간다. 식별자(ISBN·전화번호 등)는 정규화한 형태로 저장·비교한다. 시험 실행 두 곳에서 모두 입력 경계에서 문제가 났다(ticket-booking: DB 전용 입력, 샌드박스: 비 ASCII 숫자).
- **검사**: 제약(예: 요청 본문 파라미터에 `@Valid` 필수, Python 은 `.isdigit(` 금지) + 리뷰.

## C-DATA — 쿼리·트랜잭션은 어디서
- **질문**: 쿼리를 쓰는 곳(저장소만?), 트랜잭션 경계(서비스 메서드), 테스트에서 트랜잭션을 거는 방식.
- **왜 지금**: 클래스 단위 `@Transactional` 테스트가 커밋 시점의 DB 오류를 숨겨 두 번 새어 나갔다(TASK-004·014). 서비스로 쿼리가 새어 나와 나중에 제약을 더했다.
- **분류**: `mechanical`(스택 함정은 스택 파일에).
- **검사**: 제약(서비스에서 쿼리 빌더 import 금지 등) + 리뷰 체크리스트.

## C-TEST — 테스트 위치·이름·시간·픽스처
- **질문**: 테스트 파일 위치와 이름(대상 기준), 시간 고정 방법, 공용 픽스처 위치.
- **왜 지금**: 이름을 정하지 않아 중간부터 태스크 번호로 짓기 시작했다 — 프론트 테스트 33개 중 24개가 `task017.*`. 무엇을 검증하는지 이름으로 알 수 없다.
- **분류**: `mechanical`. **태스크 번호를 파일 이름에 넣지 않는다**(태스크는 끝나도 코드는 남는다).
- **검사**: 제약(`forbidden_path` — 예: `**/task[0-9]*.*`) + 리뷰.

## C-LOG — 로깅
- **질문**: 로거, 레벨 기준, 남기지 않는 것(개인정보·토큰).
- **왜 지금**: 비용 사례는 아직 없다. 다만 나중에 정하면 모든 파일을 다시 본다.
- **분류**: `mechanical`(스택 기본값).
- **검사**: 제약(`System.out`·`print(` 금지 등) + 리뷰.

## C-FE — 프론트 폴더·스타일·상태
- **질문**: 폴더(`api/`·`components/`·`pages/` …), 스타일은 토큰만(`design.md`·`design-tokens.css`), 서버 상태를 어디서 들고 있나.
- **왜 지금**: 첫 화면을 토큰 없이 만들어 다음 태스크가 화면을 다시 맞췄다(FAIL 1 + 수정 3). 하드코딩 값을 다음 태스크가 복사했다.
- **분류**: `mechanical` + `design.md` 연결. 프론트가 없으면 `해당 없음`.
- **검사**: 제약(`DESIGN-*` — 빈 저장소라 `error` 로 시작) + 리뷰.

## C-DESIGN — 설계 원칙(SOLID)을 얼마나 기계로 지키나
- **질문**: 끄기 / 신호만 / 엄격 중 무엇인가? 이 프로젝트만의 설계 방향(헥사고날·단순 3계층 등)이 있으면 결정 메모에.
- **왜 지금**: 채팅으로 "SOLID 지켜줘"라고 하면 다음 세션·Phase 4 리뷰어가 보지 못하고, 에이전트마다 해석이 달라 어떤 프로젝트는
  인터페이스를 과하게 만들고 어떤 프로젝트는 아무것도 안 한다. 정규식 제약은 글자만 봐서 SOLID 를 거의 못 거른다 —
  계층 방향(D 의 일부)만 잡고, 별칭 import 로 우회된다. ticket-booking 에서 실제 비용이 난 것은 D(계층 누수·서비스로 새어 나온 쿼리)였고
  S·O·L·I 로 재작업한 기록은 없었다.
- **선택지** (결정 칸은 이 셋 중 하나로 시작한다 — 게이트가 읽는다):

  | 단계 | 무엇을 | 원칙별 |
  |---|---|---|
  | `끄기` | 계층 방향 정규식 제약만(C-LAYOUT·C-DATA) | D 일부 |
  | `신호만` (추천) | **의존 방향을 import 구조를 읽는 도구로 막는다**(별칭·순환까지) + 복잡도·메서드 수·매개변수 수·결합도를 **너그러운 상한의 경고**로 | D 확실히, S·I 는 신호 |
  | `엄격` | 위에 더해 지표 상한을 실패로, 서비스는 포트(인터페이스)만 의존하고 구현은 조립 지점에서 주입, 포트 구현마다 **같은 계약 테스트**, 리뷰어 SOLID 체크리스트 필수 | D·S·I 기계, L 은 계약 테스트, O 는 리뷰 |

- **과한 추상화도 위반이다**: 구현이 하나뿐이고 경계(저장소·외부 호출)가 아닌 곳에 인터페이스를 새로 만드는 것은 `엄격` 에서도 리뷰 소견이다.
  포트는 경계에만 둔다.
- **분류**: `user_challenge`(프로젝트 수명·팀에 따라 갈린다) — 추천은 `신호만`.
- **검사**: 스택 파일의 도구(ArchUnit·import-linter·dependency-cruiser, PMD·ruff·ESLint 지표). `신호만` 의 지표 명령은 실패시키지 않으므로
  검사 칸에 명령을 적고 Phase 3 자체 리뷰·Phase 4 리뷰어가 그 출력을 근거로 본다.

## 코드가 있어야 아는 것 — 여기서 정하지 않는다
시험 실행에서 코드가 생긴 뒤에야 드러난 것들: 서비스로 새어 나온 쿼리, DB 전용 입력(NUL 문자·짝 없는 서러게이트), 테스트 트랜잭션이 숨기는 오류의
구체적 모양, 중첩 검증 오류의 우선순위. 이것들은 태스크가 처음 만나면 `new_conventions` 로 기록하고 회고에서 이 문서에 더한다.
