# ADR — 기술 결정 기록

결정 하나당 파일 하나. `docs/decisions/ADR-NNNN-<슬러그>.md`

## MUST

1. 검토한 선택지를 **최소 2개** 쓴다. 하나뿐이면 결정이 아니라 통보다
2. 탈락한 선택지가 **왜 탈락했는지** 쓴다 — 6개월 뒤 가장 많이 읽히는 부분이다
3. 감수하는 대가를 명시한다. 대가 없는 결정은 없다
4. 되돌리는 방법과 비용을 쓴다
5. 번호는 `docs/decisions/` 의 최대값 + 1. **재사용하지 않는다**

## FORBIDDEN

1. ❌ **기존 ADR 을 고쳐서 결정을 바꾸기** — 새 ADR 을 쓰고 이전 것을 `대체됨` 으로 표시한다
2. ❌ 선택지 1개짜리 ADR
3. ❌ 일반론 옮겨 적기 — 이 프로젝트 맥락에서의 장단점을 쓴다
4. ❌ 모든 결정을 ADR 로 만들기 (아래 §1 기준 참조)
5. ❌ 결과 섹션에 좋은 것만 쓰기

---

## 1. 무엇을 ADR로 만드는가

기준은 하나다: **이 결정이 이 태스크·이 기능을 넘어 적용되는가?**

| ADR로 만든다 | 만들지 않는다 |
|---|---|
| 상태 관리 라이브러리 선택 | 이 컴포넌트에서 useState 를 쓸지 |
| 계층 간 의존 방향 | 이 함수를 어느 파일에 둘지 |
| 인증 방식 (JWT vs 세션) | 이 엔드포인트의 파라미터 이름 |
| 특정 라이브러리를 **쓰지 않기로** 한 것 | 변수명 컨벤션 (코딩 표준으로) |
| 되돌리기 비싼 것 | 언제든 쉽게 바꿀 수 있는 것 |

**"쓰지 않기로 했다"는 결정도 반드시 기록한다.** 기록되지 않은 미도입 결정은
누군가 다시 제안할 때마다 처음부터 검토하게 만든다.

기능 문서(`features/*.md`)의 `## 7. 주요 결정 사항` 에 있는 항목 중 "범위: 전체"로
표시된 것이 승격 대상이다.

## 2. 작성

```bash
ls docs/decisions/ADR-*.md | tail -1        # 마지막 번호 확인
cp docs/decisions/_TEMPLATE.md docs/decisions/ADR-0002-<슬러그>.md
```

슬러그는 케밥케이스로, **결정의 내용**을 담는다.
`ADR-0002-layered-architecture.md` (○) / `ADR-0002-decision.md` (×)

### 맥락

결정을 **강제하는 힘**을 쓴다. 요구사항, 제약, 기존 시스템, 팀 사정.

여기까지 읽은 사람이 "그래서 뭘 골라야 하지?"라고 느껴야 맞다.
해결책을 여기 쓰면 나머지 섹션이 형식적인 정당화가 된다.

### 검토한 선택지

각 선택지의 장단점을 **이 프로젝트 맥락에서** 쓴다.

```
❌ Redis: 빠르다 / 인프라가 필요하다        (일반론)
✅ Redis: 이미 세션 저장에 쓰고 있어 추가 인프라가 없다 /
         단일 노드 구성이라 장애 시 캐시와 세션이 함께 죽는다
```

실제로 검토하지 않은 선택지를 들러리로 세우지 않는다. 진짜 후보만 쓴다.

**인증 수단(토큰·코드)을 URL 로 넘기는 결정**이면 가로채기만이 아니라 **「공격자가 만든 링크를
피해자가 열면」**을 선택지마다 검토한다 — 로그인 CSRF(피해자가 공격자 계정으로 로그인됨),
그 값이 처음 발급된 브라우저에 묶여 있는지. ADR-0021 은 가로채기만 다뤄 TASK-013 리뷰(S-1)에서
로그인 CSRF 가 뒤늦게 나왔다.

### 결정 · 이유

무엇을 골랐는지 한두 문장. 그다음 **왜 다른 것이 아니라 이것인지**.

탈락 이유를 반드시 쓴다. 이 부분이 나중에 "그때 Redis 는 왜 안 썼지?"에 답한다.

### 결과

```
- 좋아지는 것:   이 결정으로 무엇이 쉬워지나
- 감수하는 것:   무엇이 어려워지나. ★ 비워두지 않는다
- 되돌리려면:    무엇을 해야 하나. 비용은 얼마나 되나
```

"감수하는 것"이 없다고 느껴지면 아직 결정을 충분히 이해하지 못한 것이다.

### 검사 가능한 제약

이 결정에서 코드로 강제할 규칙이 나오면 `docs/architecture/constraints.yaml` 에
추가하고 여기에 ID 를 적는다. `architecture-doc` 스킬의 제약 작성 절차를 따른다.

없으면 "없음"이라고 쓴다. 빈칸으로 두지 않는다.

## 3. 완료 후

```bash
python3 scripts/rebuild_doc_index.py
git add docs/decisions/ && git commit -m "docs(adr): ADR-0002 <제목>"
```

관련 문서에서 이 ADR 을 링크한다:

- `architecture.md` 의 `## 6. 이 구조를 고른 이유`
- 승격 원본인 기능 문서의 `## 7` 표 (ADR 열에 번호 기입)
- 제약을 추가했다면 `constraints.yaml` 의 `adr:` 필드

---

## 4. 결정을 바꿀 때

**기존 ADR 을 고치지 않는다.** 과거에 왜 그렇게 판단했는지가 지워지면 같은 논의를
다시 하게 된다.

1. 새 ADR 을 쓴다. 맥락에 **무엇이 바뀌어서 재검토하게 됐는지**를 쓴다
2. 새 ADR 의 `관련` 에 이전 ADR 번호를 적는다
3. 이전 ADR 의 상태를 `ADR-NNNN 으로 대체됨` 으로 바꾼다 (본문은 그대로 둔다)
4. `rebuild_doc_index.py` 실행 — 대체된 ADR 도 인덱스에 남는다

이전 결정이 틀렸다고 쓰지 않는다. **그때는 맞았고 조건이 바뀐 것**인지,
아니면 그때 놓친 것이 있었는지를 구분해서 쓴다. 후자라면 무엇을 놓쳤는지가
다음 결정에 쓰인다.
