# 결정 대화 — 무엇을 묻고, 어떻게 묻고, 어떻게 적나

`wf-plan` Refine 단계와 `ui-mockup` 이 따른다. 기록 형식은 `docs/workflow/brief-schema.md` §4·§5.

## 1. 분류 — 묻기 전에 먼저 나눈다

| class | 무엇 | 처리 |
|---|---|---|
| `mechanical` | 코드·문서가 이미 정한 것 — 파일 경로, 재사용 대상, `architecture.md` 가 정한 계층, 관례 | 묻지 않는다. 근거와 함께 기록 (`status: approved`, `answer` 에 근거) |
| `taste` | 둘 다 괜찮은 취향 — 이름, 문구, 정렬 기본값, 순서 | 추천안으로 정하고 기록. **Lock 화면에 목록으로** 보여 주고 바꿀 수 있게 |
| `user_challenge` | 범위·약속을 바꾸는 것 | **반드시 묻는다.** 자동으로 정하지 않는다 |

**사용자 결정이 되는 것**: 범위 추가·삭제 · 완료 조건 추가·변경 · `product.md` 범위 외와 충돌 · 아키텍처에 없는
계층·컴포넌트(ADR) · 태스크 분할 · 위험 정책(동시 쓰기·권한·데이터 보존) · 영향 범위 밖이거나 2시간 넘는 보강 ·
시안의 새 화면·새 데이터 · 되돌리기 비싼 기술 선택.

애매하면 사용자 결정으로 본다. 묻지 않아도 될 것을 묻는 비용이 그 반대보다 작다.

## 2. 묻는 법 — `AskUserQuestion`

- **서로 독립인 결정은 한 번에 최대 4개.** 한 결정의 답이 다른 결정의 선택지를 바꾸면 따로 묻는다.
- 질문 문장 하나에 결정 하나. 그 질문만 보고 판단할 수 있게 맥락 한 줄을 넣는다 (다이얼로그만 보일 수 있다).
- **추천안을 첫 번째**에 두고 라벨 끝에 `(추천)`. 추천 이유는 그 선택지 설명에.
- 선택지 설명에는 **고르면 무엇이 바뀌는지** — 일정(+h), 범위, 되돌리기 비용. 장점만 적지 않는다.
- 선택지는 2~4개, 실제로 할 수 있는 것만. "기타"는 도구가 자동으로 붙인다.
- 갈림길이 접근 방식이면 `approach.options` 의 노력(S/M/L/XL)·위험·재사용을 그대로 쓴다.

```
AskUserQuestion({ questions: [{
  header: "동시 수정",
  question: "같은 매장을 두 관리자가 동시에 고치면 어떻게 할까요? (지금 코드는 잠금 없이 덮어씁니다)",
  options: [
    { label: "나중 저장을 막기 (추천)", description: "@Version 낙관적 잠금. 충돌 시 '다른 사람이 먼저 고쳤어요' 안내. +2h, 2a 에 동시 쓰기 시나리오 1건" },
    { label: "나중 저장이 이김", description: "지금 동작 유지. 먼저 고친 내용이 조용히 사라질 수 있음" },
    { label: "편집 중 잠금", description: "한 명만 편집. 잠금 해제·만료 처리가 생겨 +6h, 범위가 커짐" }
  ], multiSelect: false }] })
```

**3라운드**(질문 묶음 세 번)를 넘기면 요청이 큰 것이다. 넷째 묶음 대신 요청을 나누자고 제안한다.

## 3. 적는 법

```jsonc
{ "id": "D5", "class": "user_challenge", "source": "eng",
  "question": "같은 매장을 두 관리자가 동시에 고치면?",
  "options": ["나중 저장을 막기", "나중 저장이 이김", "편집 중 잠금"], "recommended": "나중 저장을 막기",
  "status": "approved", "answer": "나중 저장을 막기 — 안내 문구는 시안대로",
  "scope": "store 수정 API 하나. 다른 엔티티의 잠금 정책은 이 승인에 포함되지 않음" }
```

- `answer` 는 사람이 고른 선택지 + 덧붙인 말 **그대로**. 요약·해석하지 않는다.
- `scope` — 이 승인이 덮는 범위. 비슷한 다른 곳에 같은 답을 쓰려면 다시 묻는다.
- 미룬 것은 `deferred` — Lock 때 `out_of_scope` 와 후속 태스크 후보로 보여 준다.
- 확정 뒤 다시 열면 `reopened` + `reopened_in: "<Phase>"`. 다시 답을 받으면 `approved`.

## 4. 완전성 보강 — 영향 범위 안에서만

Eng 리뷰가 낸다. 영향 범위 = 변경 대상 파일 · 그 파일을 직접 쓰는 쪽 · 그 파일들을 건드리는 테스트 ·
같은 입력을 받는 형제 엔드포인트 · (화면이면) 범위 안 화면의 상태 화면.

| 조건 | 처리 |
|---|---|
| 영향 범위 안 **그리고** 새 기능이 아니라 기존 완료 조건을 완성 **그리고** +2h 이하 **그리고** 태스크 16h 이하 | `completeness` 에 `included` — 묻지 않고 넣되 Lock 화면에 보여 준다 |
| 하나라도 아니면 | `user_challenge` 결정 — 추가 / 후속 태스크로 미룸 / 제외 |

## 5. 이벤트

질문과 답의 시각은 훅이 자동으로 남긴다(`AskUserQuestion` 전후). 그 밖의 것은 직접:

```bash
python3 scripts/wf_event.py --id REQ-003 --event review_finding --data '{"role":"eng","class":"user_challenge"}'
python3 scripts/wf_event.py --id REQ-003 --event finding_applied --data '{"role":"eng"}'
```

회고(`/wf-retro`)가 역할별 채택률과 다시 열린 결정을 센다 — 채택된 소견이 오래 없는 역할은 기본으로 끈다.
