# Phase 1 설계 점검 — 놓치기 쉬운 네 가지

`wf-plan` Step 1.5 · 2 · 4 에서 참조한다. 모두 **실사용에서 Phase 2a·4 까지 가서야 드러난**
것들이다. 각각 Phase 1 에서 5분이면 확인된다.

---

## 1. 화면 간 이동도 flow 다 (Step 4 — route 가 Frontend 일 때)

`design.flows` 에 **화면 안의 상태**(기본·로딩·빈·오류)만 적고 **화면 사이의 이동**을
빼기 쉽다. 이동이 flow 에 없으면 구현 단계에서 링크를 추가하고도 범위 이탈로 기록되지
않아, Phase 4 의 `scope_deviations` 대조에서야 사후 발견된다.

route 가 `Frontend` 이면 **최소 1개 flow 가 화면 간 이동**이어야 한다.

```jsonc
{ "id": "F5", "name": "목록 카드 → 상세 이동",
  "covers": ["AC-1"], "steps": ["카드 클릭", "/performances/:id 로 이동"] }
```

이동이 하나도 없는 화면(단일 화면 앱)이면 `route_reason` 에 그렇게 적는다.

## 2. 외부 리소스·프리셋 값은 사용처부터 본다 (Step 2)

웹폰트 굵기, 라이브러리 테마 프리셋, CDN 에서 받는 에셋 버전처럼 **요청 파라미터로 값을
지정하는** 것은, 지정하기 전에 **실제로 쓰는 곳의 현재 값**을 코드베이스에서 먼저 확인한다.

임의로 정하면 쓰지 않는 값을 받거나(굵기 600·700 을 요청했는데 실사용은 400·500),
쓰는 값을 못 받는다. 그 차이가 렌더에서 드러나는 것은 Phase 4 다.

## 3. 타입을 넓히는 변경은 새로 열린 입력 범위를 적는다 (Step 4)

`Integer → BigDecimal`, `int → long`, `enum → String` 처럼 **받을 수 있는 값의 범위가
넓어지는** 변경이 포함된 태스크는, `design.unresolved` 에 **"이 변경으로 새로 도달
가능해지는 입력 범위"** 를 적는다.

```jsonc
"unresolved": [
  "price: Integer → BigDecimal. 새로 도달 가능: 소수, 지수 표기(1e400), int 범위 초과값"
]
```

`coverage-policy.md` §2-1 의 타입별 표는 **바뀐 뒤의 타입**에 대본다. 타입이 바뀌면서
생기는 새 입력 공간은 **바뀌기 전과 비교해야** 보인다 — 표만으로는 놓친다.

## 4. ADR 이 이 태스크를 지목하는지 본다 (Step 1.5)

ADR 은 본문을 읽는 데서 끝나지 않는다. **「검사 가능한 제약」 절을 열어, 이 태스크를
지목하는 항목이 있는지** 확인한다.

```
ADR-0010 §검사 가능한 제약
  - ARCH-004: @RequestBody 에는 @Valid 가 있어야 한다 — 마이그레이션 태스크가 생기면
    그 안에서 추가한다          ← 이 태스크를 가리키는 문장
```

있으면 그 항목을 `codebase_analysis.target_files` 에 반영한다. 읽고도 놓치면 Phase 4 의
코드 리뷰어가 처음 발견하게 되고, 그때는 Phase 3 으로 되돌아간다.
