# 시험 — Phase 1 코드베이스 조사를 `Explore` 에 맡기기

`wf-plan` Step 2 에서 참조한다. **시험이다.** 3개 태스크를 돌린 뒤 아래 기준으로 유지·철회를 정한다.

## 무엇을 보려는가

정확도를 높이려는 것이 **아니다.** 인라인 조사의 정확도는 이미 높았다(아래 기준선). 보려는 것은
정확도를 잃지 않으면서 **메인 컨텍스트에 쌓이는 파일 읽기를 줄일 수 있는가**다. 조사는 읽을 것은
많고 남길 것은 적어서(`codebase_analysis` 몇 줄) 격리하기 좋은 작업이고, Phase 1 안에는 사람에게
물을 일이 없다.

정확도로 얻을 것은 없고 잃을 수만 있다. 그래서 `check_plan.py` 가 경로를 기계로 확인한다 —
요약으로 받은 경로를 믿지 않는다.

## 기준선 — 인라인 조사 (ticket-booking 11개 태스크, 각 PLAN 이 처음 커밋된 시점의 파일 존재 기준)

| 항목 | 값 |
|---|---|
| 표시 없이 존재하지 않는 경로 (지어낸 경로) | 0건 |
| 경로 표기 오류 (`check_plan.py` 위반) | 1건 — TASK-008, 한 항목에 두 파일 (`develop` 의 10건에 실행. TASK-009 는 당시 브랜치에만 있어 제외) |
| `target_files` 중 새 파일 | 44/76 (58%) |
| `unresolved` | 평균 3.3건 (TASK-009 만 11건) |
| Phase 3 `scope_deviations` | 평균 0.8건 — 조사가 빠뜨린 파일의 대리 지표 |

## 호출

```
Agent({
  subagent_type: "Explore",
  description: "TASK-001 코드베이스 조사",
  run_in_background: false,
  prompt: `
TASK-001 의 구현 계획을 위해 코드베이스를 조사해주세요. 코드를 고치지 않습니다.

태스크: <title>
완료 조건:
<acceptance_criteria 를 그대로>
관련 아키텍처: <architecture.md 의 해당 계층 · 참조 ADR 번호>

찾을 것 (thoroughness: medium):
1. 변경 대상 파일 — 고칠 기존 파일과, 새로 만들어야 할 파일을 구분
2. 재사용할 것 — 기존 유틸리티 · 데코레이터 · 베이스 클래스 · 테스트 지원 클래스
3. 변경이 파급되는 파일 — 바꿀 함수를 호출하는 곳
4. 기존 테스트 — 위치, 패턴, 실행 명령
5. (Frontend) 화면이 기대는 API 응답 필드가 백엔드 응답 DTO 에 실제로 있는지 — 필드를 만드는 코드의 위치

출력 형식 (이 형식만):
- 경로는 **저장소 기준 상대경로 하나씩**, 항목마다 한 줄. 쉼표로 묶지 않는다
- 기존 파일은 실제로 열어 확인한 것만 적고, 근거로 \`경로:줄\` 과 심볼을 붙인다
- 새로 만들 파일은 "신규" 라고 표시하고, 같은 패턴의 기존 파일을 하나 근거로 든다
- 찾지 못한 것은 "못 찾음" 으로 따로 적는다. 추측으로 채우지 않는다
`
})
```

받은 뒤:

1. 보고를 `codebase_analysis` 로 옮긴다. 새 파일은 `"new": true`
2. `design.inputs` · `outputs` 를 정하는 데 필요한 파일만 **직접** 연다. 연 파일 수를
   `exploration.main_reads` 에 적는다 — 이 수가 크면 시험의 이득이 없다는 뜻이다
3. 보고가 부족하면 같은 에이전트에 이어 묻거나 인라인으로 보충하고 `calls` 를 늘린다
4. `python3 scripts/check_plan.py --task-id <ID>` — 위반이 있으면 고친다. **요약을 믿지 않는다**

```jsonc
"exploration": {
  "method": "explore",          // explore | inline (Explore 를 못 쓰면 inline 으로 하고 그렇게 적는다)
  "calls": 1,                   // Explore 호출 횟수
  "main_reads": 2               // 보고를 받은 뒤 메인이 직접 연 파일 수
}
```

## 판정 — 3개 태스크 후

| 기준 | 유지 | 철회 |
|---|---|---|
| `check_plan.py` 첫 실행에서 지어낸 경로 | 0 | 1건이라도 |
| `unresolved` | 기준선과 비슷 | 체계적으로 늘었다 |
| Phase 3 `scope_deviations` | 기준선(0.8) 수준 | 늘었다 — 조사가 빠뜨린다 |
| `main_reads` | 작다 | 메인이 결국 다 다시 읽었다 — 이득이 없다 |
| 체감 (세션 길이 · 대기) | 사람이 판단 | |

**철회하려면** `wf-plan` Step 2 의 시험 표시와 이 문서를 지운다. `check_plan.py` 와 `new` 필드는
시험과 무관하게 남긴다 — 인라인 조사에도 필요한 검사다.

## 한계

- 토큰은 산출물에 기록되지 않는다. 메인 컨텍스트 절감은 `main_reads` 와 사람의 체감으로만 본다
- `Explore` 는 Claude Code 내장 에이전트라 모델·도구를 우리가 정하지 않는다
- 3개 태스크는 작은 표본이다. 판정이 애매하면 기간을 늘린다
- `check_plan.py` 는 경로가 *있는지*만 본다. 맞는 파일인지, 빠뜨린 파일이 없는지는 Phase 3 의
  `scope_deviations` 로 나중에 드러난다
