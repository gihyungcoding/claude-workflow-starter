# 프로덕트 정의 · 기능 요구사항

두 종류의 문서를 다룬다.

| 문서 | 답하는 것 | 언제 |
|---|---|---|
| `docs/product/product.md` | 무엇을 왜 만드는가. 누구를 위한 것인가 | 프로젝트 초기, 방향이 바뀔 때 |
| `docs/product/features/<이름>.md` | 이번에 무엇을 만드는가. **어떤 태스크로 쪼개지는가** | 기능마다 |

## MUST

1. 요구사항 문서에는 **`## 1-2. 태스크 분리` 표를 반드시 채운다.** 이 표가 `tasks.json` 이 된다
2. `## 범위 외` 를 비워두지 않는다 — 무엇을 안 하는지가 경계를 만든다
3. `## 구현 참고` 에 **실제 파일 경로·클래스·함수·엔드포인트를 그대로** 쓴다
4. 완료 조건은 Task별 체크박스로, **관찰 가능한 문장**으로 쓴다
5. 파일명은 케밥케이스 (`store-search-permission.md`)
6. **화면이 있으면 §2 화면 설계를 §3 API 보다 먼저 채운다.** 특히 `2-2 참조` 를
   건너뛰지 않는다 — 도메인을 모르면 무엇이 빠졌는지 모른다

## FORBIDDEN

1. ❌ §1-2 를 비운 채 문서를 완료 처리 — 태스크 추출이 불가능해진다
2. ❌ 코드 참조를 추상적으로 쓰기 ("매장 서비스를 수정한다")
3. ❌ 백엔드와 프론트엔드를 §1-2의 한 행에 묶기
4. ❌ mermaid·이미지 다이어그램 — 문서 안에서는 ASCII (grep·LLM 친화)
5. ❌ 측정 수단 없는 완료 조건 ("사용성이 좋아진다")

## product.md 작성

`docs/product/product.md` 의 TODO 를 채운다. 대화로 끌어낸다 — 사용자가 이미 아는 것을
문서 형식으로 옮기는 일이다.

물어볼 순서:

1. **한 문장** — "이게 뭔가요?" 한 문장으로 못 쓰면 아직 정의가 안 된 것이다
2. **문제** — 해결책 말고 문제를 묻는다. "지금 누가 무엇 때문에 곤란한가요?"
3. **사용자** — 역할 이름은 나중에 태스크의 `sub_categories` 가 되므로 여기서 확정한다
4. **범위** — 하는 것보다 **하지 않는 것**을 더 집요하게 묻는다
5. **성공 기준** — "무엇이 관찰되면 성공인가요? 어떻게 측정하죠?"
6. **제약** — 마감·규제·기존 시스템·팀 규모
7. **열린 질문** — 아직 답이 없는 것. 없다고 하면 한 번 더 묻는다

각 섹션을 채운 뒤 사용자에게 확인을 받고 다음으로 넘어간다. 한 번에 다 물어보지 않는다.

작성 후 `CLAUDE.md` 의 `sub_categories` 목록을 3번에서 정한 역할로 채운다.

## 기능 요구사항 문서 작성

```bash
cp docs/product/features/_TEMPLATE.md docs/product/features/<케밥-이름>.md
```

### 순서

**1. 배경** — 무엇이 문제이고 왜 지금인가. 4~6줄.

**2. 화면이 있으면 §2 화면 설계** — 없으면 이 섹션을 지우고 3번으로.

이 섹션이 §3 API 와 §5 완료 조건을 결정하므로 먼저 쓴다. 반대로 하면 화면에 필요한
필드가 데이터 모델에 없는 채로 구현까지 간다.

| 절 | 무엇 | 놓치면 |
|---|---|---|
| 2-1 | 사용자가 하려는 일 (한 문장) | 우선순위를 정할 기준이 없다 |
| **2-2 참조** | 비슷한 상용 서비스를 열고 대조 | **무엇이 빠졌는지 모른다** |
| 2-3 담기는 것 | 요소 + 데이터 출처 | 없는 필드를 구현 단계에서 발견한다 |
| 2-4 배치 | ASCII 와이어프레임 | 구조가 부족한 걸 화면을 만든 뒤에 안다 |
| 2-5 상태 | 기본/로딩/빈/오류 | 완료 조건이 기본 상태만 덮는다 |

**2-2 가 이 섹션의 존재 이유다.** 실제 서비스를 하나도 안 보고 "카드에 제목·날짜"
같은 결론을 쓰면, 그 결론이 그대로 데이터 모델까지 간다. 사용자가 참조를 주지
않으면 직접 찾아 제시한다.

2-3 의 **「데이터 출처」가 빈 행은 새 필드**다. 하나라도 있으면 §3 명세와
마이그레이션이 필요하고 백엔드 태스크가 커진다 — 사용자에게 명시적으로 알린다.

**3. 나머지 상세** (§1-3, §3, §4). 무엇을 만들지 모르면 태스크를 쪼갤 수 없다.

**4. §1-2 태스크 분리 — 이 문서의 핵심**

상세를 다 쓴 뒤에 쪼갠다. 각 행에 대해:

| 열 | 어떻게 |
|---|---|
| Task | `A. 백엔드 — <무엇>` 형식. 한 행 = 한 태스크 |
| 범위 | 어디까지 하는가 |
| 산출물 | API 엔드포인트, 화면, 스키마 |
| 포함하지 않음 | **비우지 않는다.** 범위가 새는 지점이다 |
| 선행 | FE 행은 BE 행을 반드시 적는다 |
| 추정 | 4~16h. 벗어나면 행을 합치거나 나눈다 |
| 태스크 ID | **비워둔다.** `/wf-tasks-from-doc` 이 채운다 |

쪼갤 때 `task-authoring` 스킬의 WRU 판정 기준을 그대로 쓴다. 특히:

- 한 행이 4시간 미만이면 인접 행과 합친다
- "원인 분석만", "QA만", "스펙 정의만" 하는 행을 만들지 않는다 — 구현 행에 흡수시킨다
- 백엔드와 프론트엔드는 항상 다른 행

**분리 이유**를 한두 문장 적는다. 나중에 "왜 이렇게 쪼갰지?"를 되짚을 때 필요하다.

**4. §4 완료 조건** — Task별 체크박스. 그대로 `acceptance_criteria` 가 된다.

**5. §5 구현 참고** — 코드베이스를 실제로 찾아본 뒤 쓴다 (Grep/Glob). 이 섹션이
태스크 추출 품질을 결정한다. 없는 파일이면 `(신규)` 로 표시한다.

화면 작업이면 **화면 명세**도 채운다. 순서가 중요하다 — 상세(§1-3)나 API(§2)보다
**화면을 먼저** 적는다. 화면이 필요로 하는 데이터가 API 요구가 되기 때문이다.
반대로 하면 "만들고 보니 이 필드가 없다"가 된다.

#### 시안이 없을 때 (흔한 경우)

시안이 없어도 구현은 된다. 세 가지만 있으면 충분하다.

1. **UI 라이브러리** — `CLAUDE.md` 에 적힌 것. 없으면 여기서 멈추고 정하자고 제안한다.
   버튼·입력·모달의 생김새는 라이브러리가 정하므로, 정해두면 디자인 결정의 대부분이 사라진다
2. **화면 목록과 상태** — 표로
3. **상태별로 무엇이 보이는가** — 글로. "예쁘게"가 아니라 "무엇이 있는가"

빠뜨리기 쉬운 상태를 **먼저 묻는다**: 빈 목록 · 로딩 · 오류 · 권한 없음 · 텍스트가 아주 길 때 ·
항목이 아주 많을 때. 시안이 있는 프로젝트도 이 상태들이 빠져 있는 경우가 대부분이다.

#### 목업이 필요하면

글로 설명이 안 되거나 배치를 눈으로 확인하고 싶을 때, `design` 스킬로 화면 목업을
Artifact 로 만들 수 있다. 여러 화면을 한 캔버스에 놓고 볼 수 있다.

**먼저 제안하지 않는다.** 사용자가 글 명세로 충분하다고 느끼면 그게 맞다 —
목업은 만드는 데 시간이 들고, 만들면 그것에 맞추느라 구현이 느려질 수 있다.

#### 시안이 있을 때

링크만 건다. 이미지를 저장소에 복사하지 않는다 — 원본이 바뀌면 사본은 조용히 낡는다.
링크가 있어도 **상태별 명세는 그대로 쓴다.** 시안에 없는 상태가 반드시 있다.

**6. §6 범위 외** — "나중에 할 수도 있는 것"과 "하지 않기로 한 것"을 구분한다.

**7. §7 주요 결정 사항** — 각 결정에 대해 **"이 기능을 넘어 다른 곳에도 적용되는가?"**
를 묻는다. 그렇다면 `/wf-adr` 로 승격시킨다. 기능 문서에 갇힌 결정은 기능이 끝나면
아무도 찾지 못한다.

### 완료 후

```bash
python3 scripts/rebuild_doc_index.py
```

사용자에게 다음을 안내한다:

```
docs/product/features/store-search-permission.md 작성

  태스크 분리   2건 (Backend 8h → Frontend 6h)
  완료 조건     5건
  ADR 승격 후보 1건 — "권한 판정을 데코레이터로 통일"

  다음: /wf-tasks-from-doc docs/product/features/store-search-permission.md
```

## 기존 문서 갱신

- **상태**를 바꾼다 (초안 → 확정 → 구현 중 → 완료)
- **최종 갱신** 날짜를 고친다
- 확정된 내용에는 인라인으로 `[확정 2026-09-01]` 을 남긴다
- 이미 태스크가 생성된 문서의 §1-2 표를 고칠 때는 **태스크 ID 열을 지우지 않는다** —
  문서와 태스크의 양방향 추적이 끊긴다. 태스크 자체를 바꿔야 하면 사용자에게 알린다
