# 커버리지 정책 — 시나리오를 몇 개 쓸 것인가

---

## 1. 기준: 개수가 아니라 매핑

**"시나리오 N개"라는 목표를 세우지 않는다.** 개수를 목표로 하면 채우기 위한 시나리오가
생긴다. 기준은 하나다:

> 모든 `acceptance_criteria` 가 최소 1개 시나리오에 대응하는가?

이것을 만족하면 충분하고, 만족하지 않으면 몇 개를 썼든 부족하다.

---

## 2. 하한

| 조건 | 최소 |
|---|---|
| 전체 | 2건 |
| `happy` | 1건 |
| `error` | 1건 |

`error` 시나리오가 없는 태스크는 거의 없다. 없다고 판단했다면 다음을 확인한다:

- 입력이 잘못되면 어떻게 되는가?
- 권한이 없으면 어떻게 되는가?
- 대상이 존재하지 않으면 어떻게 되는가?
- 외부 의존(DB·API)이 실패하면 어떻게 되는가?

이 중 하나도 해당하지 않는 경우에만 `error` 를 생략하고, **생략 이유를 시나리오 문서에 적는다.**

### 2-1. 입력을 받는 태스크 — 타입별 경계값 하한

**요청 본문·쿼리 파라미터를 받는 태스크는 아래 표를 입력 필드에 하나씩 대본다.**
해당하는 행마다 시나리오가 최소 1건 있어야 한다.

**이 표는 `scripts/coverage_matrix.py` 의 `KINDS` 와 짝이다.** Phase 1 이 필드마다 종류를 고르면
(`design.input_fields`) 스크립트가 아래 경계를 칸으로 펼치고, 2a 게이트가 빠진 칸을 센다. 행을
더하거나 경계를 바꾸면 `KINDS` 도 함께 고치고 `--check-policy` 로 맞는지 확인한다 — 표에만 있는
경계는 아무도 세지 않는다. 표 첫 열의 `` `kind` `` 표기가 그 대응이다.

```bash
python3 scripts/coverage_matrix.py --kinds     # 종류 이름과 칸
```

| 입력 타입 | 반드시 확인할 경계 | 놓치면 |
|---|---|---|
| 문자열 `string` | 빈 값·공백만, **유니코드 공백만**(U+3000·NBSP·U+200B·U+2028), **최대 길이 + 1** | DB 제약에서 500. 정규식 `\S`·검증 애노테이션·언어의 공백 판정 함수가 '공백'을 서로 다르게 봐서 필드마다 판정이 어긋난다 (실사용: 같은 묶음의 두 필드 중 하나만 전각 공백을 통과시켰다) |
| 정수 `integer` | 음수, 0, **상한 + 1**, **소수**(`1.9`), 타입 범위 초과 | 소수가 정수로 절삭돼 검증 우회, 범위 초과로 500 |
| 정수 필드의 **표기 변형** (JSON·토큰 클레임처럼 외부가 숫자를 적는 곳) `integer_notation` | **숫자 문자열**(`"1700000000"`), **정수값 소수**(`1700000000.0`), **지수**(`1.7e9`), 받는 타입(`long`·`Instant`)의 **표기 범위 초과** | 파서가 문자열·소수를 조용히 정수로 받아 주거나, 범위 초과가 500 으로 새어 나간다 (TASK-016 V11 2·3회차) |
| 요청에 실린 **불투명 문자열** (토큰·코드·서명) `opaque` | 앞뒤에 붙은 문자(`=`·`~`·공백·LF·NUL·서로게이트·비 ASCII)를 **실제 입구**(HTTP 요청)로 보낸다. 내부 메서드 직접 호출로 대신하지 않는다 | 바인딩·trim·디코딩이 입구에서 문자열을 바꿔 서명 검증을 통과한다. 직접 호출 테스트는 그 계층을 거치지 않는다 (TASK-016 `request_string`) |
| **여러 파라미터로 분기하는 입력** (예: `token` 과 `pendingToken`) `multi_param` | 파라미터마다 빈·공백·유효 값의 **모든 조합**을 한 표로 — 한쪽 빈 + 다른 쪽 유효, 둘 다 값, 둘 다 없음 | 한 조합의 분기가 빠져 엉뚱한 흐름으로 간다 (TASK-013 V11 1회차 — `token` 빈 값 + `pendingToken` 유효) |
| 배열 `array` | 빈 배열, **null 원소**, **최대 개수 + 1** | null 원소로 500, 대량 입력으로 DoS |
| 필수 필드 `required` | 누락, `null` | 기본값으로 조용히 저장 |
| JSON 본문의 필드 `json_field` | 다른 JSON 타입(숫자·객체·배열·불리언) | 역직렬화가 타입을 바꿔 받아 주거나 500 이 난다 |
| JSON 요청 본문 자체 `json_body` | 본문 비어 있음, JSON 아님 | 파싱 예외가 400 이 아니라 500 으로 새어 나간다 |
| 열거형 `enum` | 정의 밖 값, **정의된 값 각각** (필터라면) | 값 하나만 잘못 동작해도 안 보인다 |
| 시각 `datetime` | `now == 경계` — **같은 비교를 하는 코드 경로마다** | 단건 조회는 맞고 목록 필터는 틀린다 |
| 환경변수·헤더 값 `config` | **미설정**, 빈 문자열, 공백만, **대소문자**(`TRUE`), **표기 변형**(`1`·`yes`), 쉼표 목록의 **연속 구분자·앞뒤 공백**, **접두사만 일치**하는 값, 헤더 자체의 부재 | 빈 원소가 전체 허용으로 오인되거나, 비표준 값에 조용히 꺼진 채 기동된다 |
| 문자열 필드 **전수** (저장·비교되는 값) `string_stored` | 필드마다 **NUL**, **짝 없는 서로게이트**, 정규화·대소문자 변환 후 길이·동일성. 로그인·조회처럼 **저장값과 비교만 하는 입력**도 포함 | DB 가 무손실로 저장하지 못하는 값이 `?` 로 치환돼 409 오보·다른 값과 충돌·비밀번호 매칭(200)이 된다. 테스트 DB(H2)는 받아 주어 통과한다 |
| 서버 응답의 `code`·본문으로 분기하는 로직 `server_response` | 같은 상태에 **다른 code**, **빈 바디**, **비 JSON** 본문 | 상태만 보고 분기하는 단순 구현이 모든 시나리오를 통과한다 |
| 에러 상태를 켜는 시나리오 `error_state` | **재제출 시 꺼짐**을 같은 표에 묶는다 | 초기화 코드를 지워도 모든 테스트가 통과한다 |
| 비동기 결과를 상태에 적용하는 곳 `async_result` | 개별 응답이 아니라 **응답이 오는 사이 무엇이 바뀔 수 있는가** — 시작 이후의 로그인·로그아웃·언마운트·화면 이동·StrictMode 취소, 늦게 오는 성공·401·5xx·네트워크 오류·비 JSON | 늦게 온 응답이 이미 바뀐 상태를 덮어쓴다. 정상 흐름만 덮은 118케이스가 통과했다 (TASK-010) |
| 클라이언트 라우터·서버가 **경로로 판별하는 주소** `route_path` | **끝 슬래시**, **대소문자**, 같은 경로의 **퍼센트 인코딩**, **깨진 인코딩** | 판별을 다시 구현한 코드가 표기 변종 하나씩에서 라우터와 다른 결과를 낸다 (실사용: 정확 일치 → `matchPath` → `matchRoutes` 로 세 번 고침) |
| **외부 URL 입력** (이미지·링크) `url` | 스킴 대소문자, 호스트의 **밑줄·비 ASCII·`%XX`·`:` 여럿**, **빈 userinfo·userinfo 안 `@`**, **빈 포트·비 ASCII 숫자 포트**, IPv6 리터럴, 앞뒤 공백 — 하위 요소마다 받을지 거부할지 규약에 적는다 | 'https 절대 URL' 한 줄이면 URL 파서의 판정에 기대게 되고, 리뷰마다 하위 요소 변종이 하나씩 나온다 (실사용: 리뷰 4라운드, 시나리오 롤백 2회) |
| 프레임워크가 외부 입력을 **변환한 뒤** 판정에 쓰는 값 (OIDC 디코더의 클레임 변환, 역직렬화, 컨버터) `converted` | Given 에 **변환 전 원문**과 **변환 후** 중 어느 쪽인지 적는다. 판정을 검증하는 시나리오는 **변환 계층을 실제로 통과시키는** 테스트와 짝으로 둔다. 값마다 대소문자·앞뒤 공백·숫자 표기·타입 변형 | 사양은 '정확히 "true" 만 검증됨'인데 프레임워크가 "TRUE" 도 true 로 바꿔 운영에서 사양과 달랐다. attributes 를 직접 주입한 테스트는 변환을 우회해 그대로 통과했다 (TASK-012 RC-1) |

**직접 주입 테스트는 변환 계층을 증명하지 못한다.** 핸들러·서비스 테스트가 `attributes`·DTO 를 직접
넣으면 프레임워크의 클레임 변환·역직렬화·바인딩을 거치지 않는다. 사양이 외부 입력의 *타입이나
값 표기*에 걸려 있으면(검증됨 플래그, 권한 문자열, 열거형 표기) 같은 값을 실제 입구에서
통과시키는 시나리오를 하나 둔다. 직접 주입 시나리오는 판정 로직을, 입구 시나리오는 변환을 지킨다.

**이 표가 있는 이유** — 실사용에서 Phase 4 가 FAIL 을 낸 결함의 대부분이 이 표의 굵은
글씨였다. 시나리오에 없으면 Red 테스트도 없고, 구현은 그 경계를 처리하지 않은 채
Green 이 되며, Phase 4 의 코드 리뷰가 실제 요청으로 재현해서야 드러난다. 그때는 2a 로
되돌아가 2b·3 을 다시 거쳐야 한다. **경계값은 Phase 4 가 찾을 일이 아니라 여기서 쓸 일이다.**

**환경변수·헤더는 "입력이 아니라 설정" 이라고 건너뛰기 쉽다.** 그러나 값이 잘못됐을 때
조용히 열리거나(fail-open) 닫히는 동작이 여기서 결정된다. 독립검증(V11)이 라운드마다 하나씩
새 경계를 지적해 재시도 상한을 소진한 사례가 있다 — 1차 작성에서 위 행을 한 번에 대본다.

**문자열 필드는 한 필드에서 결함이 나오면 같은 타입의 모든 필드·경로에 있다.** TASK-009 는 이
행을 필드마다 한 번씩만 대본 탓에 Phase 4 가 같은 뿌리로 4번 FAIL 했다(name NUL → 이메일 →
로그인 password). 1차 작성에서 입력 문자열 필드를 표로 열거해 한 시나리오로 묶고, 검증은
필드마다가 아니라 공통 지점에서 막는다. 테스트 DB 가 운영 DB 와 다르면 Plan 의 test_strategy 에
운영과 같은 엔진의 통합 테스트를 적는다.

**칸은 1차 작성에서 전부 닫는다.** `coverage_matrix.py --skeleton` 이 아직 판정하지 않은 칸을
모두 보여준다. 지적된 칸만 고치는 식으로 회차를 돌면 같은 일이 반복된다 (TASK-016 V11 FAIL 9회).

#### 개수를 불리지 않는 법

필드가 여러 개여도 **같은 검사는 시나리오 하나에 표로 묶는다.**

```
SC-07 (error) 문자열 필드가 최대 길이를 넘으면 400

  | 필드  | 최대 | 입력 길이 |
  |-------|------|-----------|
  | title | 200  | 201       |
  | venue | 200  | 201       |
```

**검사가 다르면 묶지 않는다** — 아래 §3 의 판단 기준이 그대로 적용된다.

### 2-2. 하나의 판정이 여러 항목에 걸칠 때

서버가 여러 항목을 합쳐 한 번 판정하고 **어느 항목이 문제인지 특정하지 않는** 경우
(예: 구역 여러 개의 좌석 총합이 상한 초과), 화면이 그 결과를 **어느 항목 옆에** 보여줄지를
이 단계에서 정한다. 항목 1개짜리 시나리오만 있으면 다중 항목에서의 동작이 Phase 4 까지
검토되지 않는다.

## 3. 상한 — 언제 그만 쓰는가

시나리오를 추가하기 전에 물어본다:

> 이 시나리오가 실패했을 때, **기존 시나리오는 통과하면서** 이것만 실패하는 코드 결함이
> 실제로 존재할 수 있는가?

없으면 그 시나리오는 중복이다.

**같은 코드 경로를 타는 입력들은 하나로 묶는다.**

```
❌  SC-03  첫 페이지를 요청하면 20건이 반환된다
    SC-04  마지막 페이지를 요청하면 나머지가 반환된다
    → 같은 페이지네이션 코드. 결함이 있으면 둘 다 깨진다.

✅  SC-03  결과가 20건을 넘으면 페이지로 나뉜다 (경계 포함)
```

**같은 검증 수단이어도 위반 조건이 다르면 묶지 않는다.** `@NotBlank`(빈 문자열)와
`@Pattern`(형식 오류)은 둘 다 Bean Validation 이지만 서로 다른 입력에서 따로 실패한다.
하나로 묶으면 한쪽은 테스트 안전망 없이 넘어간다. 판단 기준은 도구가 아니라 **입력**이다.

묶은 경우 **왜 묶었는지를 체크포인트의 `decisions` 에 기록**한다. 나중에
"경계 케이스가 없다"는 지적을 받았을 때 판단 근거가 남아 있어야 한다.

## 4. 태스크 복잡도별 기준선

`tasks.json` 의 `meta.complexity.level` 을 참고한다. **목표가 아니라 감각의 기준선**이다.

| level | 대략 | 이보다 훨씬 적다면 | 이보다 훨씬 많다면 |
|---|---|---|---|
| 단순 | 2~3건 | acceptance_criteria 매핑 확인 | 중복 확인 |
| 보통 | 4~7건 | 오류 경로를 덜 봤을 가능성 | 태스크가 너무 큰 것 아닌지 |
| 복잡 | 8~12건 | 흐름을 놓쳤을 가능성 | 태스크 분할 검토 |

12건을 넘으면 대개 태스크가 WRU보다 크다. 진행 전에 사용자에게 알린다
(→ `docs/workflow/task-schema.md` §1 크기 기준).

## 5. 커버리지 기록

`SCENARIO_<ID>.json` 에 매핑 결과를 남긴다.

```jsonc
"coverage": {
  "acceptance_criteria_total": 3,
  "acceptance_criteria_covered": 3,
  "uncovered": [],
  "merged": [
    { "scenarios": ["첫 페이지", "마지막 페이지"],
      "into": "SC-03",
      "reason": "같은 페이지네이션 코드 경로" }
  ]
}
```

`uncovered` 가 비어 있지 않으면 EXIT GATE를 통과하지 못한다.
덮을 수 없는 기준이 있다면 그건 **이 태스크의 범위가 아니거나**, 자동 검증이 불가능한
기준(수동 QA 등)이다. 후자라면 태스크 정의를 고쳐야 한다는 신호이므로 사용자에게 알린다.

## 6. 회귀 시나리오

기존 동작을 바꾸는 태스크에는 `regression` 시나리오를 넣는다.

```markdown
## SC-05 (regression) 기존 전체 조회가 그대로 동작한다

- **Given** 관리자 A는 모든 매장에 접근할 수 있다
- **When** A가 매장 목록을 조회한다
- **Then** 모든 매장이 반환된다
```

권한 필터를 추가하면서 관리자 경로를 깨뜨리는 것이 이 종류 태스크의 전형적 사고다.
"무엇을 깨뜨릴 수 있는가"를 한 번은 명시적으로 묻는다.
