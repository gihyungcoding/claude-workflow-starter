# Canonical GWT 작성 규칙

시나리오 한 건을 어떻게 쓰는가.

---

## 1. 구조

```
Given   시작 상태 — 이미 참인 사실
When    단일 행위 — 무엇을 하는가
Then    관찰 가능한 결과 — 밖에서 확인할 수 있는 것
```

- `Given` 은 여러 개 가능 (`And` 로 연결)
- **`When` 은 하나다.** 두 개가 필요하면 시나리오를 나눠야 한다
- `Then` 은 여러 개 가능하되, 전부 같은 `When` 의 결과여야 한다

---

## 2. Then 은 관찰 가능해야 한다

테스트가 단언할 수 없는 것은 Then이 아니다.

| ❌ 관찰 불가 | ✅ 관찰 가능 |
|---|---|
| "내부적으로 캐시된다" | "두 번째 호출의 응답 시간이 100ms 미만이다" |
| "권한이 올바르게 처리된다" | "403이 반환된다" |
| "데이터가 정상 저장된다" | "조회 시 저장한 값이 그대로 반환된다" |
| "성능이 개선된다" | "응답 시간이 기존 대비 20% 이내 증가한다" |

판단 기준: **이 문장을 그대로 `assert` 로 옮길 수 있는가?**
못 옮기면 다시 쓴다.

### 스타일·테마 값은 설정이 아니라 렌더 결과를 본다

색·굵기·모서리·구분선 같은 **화면에 보이는 값**을 다루는 시나리오는, Then 을 **설정 객체와의
대조**(`theme.palette.primary.main == ...`)가 아니라 **렌더된 결과**(`getComputedStyle`,
실제 DOM 의 스타일)로 쓴다.

| ❌ 설정을 본다 | ✅ 렌더를 본다 |
|---|---|
| "테마의 primary 색이 `#0E6E52` 이다" | "예매가능 배지의 배경색이 `rgb(14, 110, 82)` 이다" |
| "typography.h6 의 굵기가 500 이다" | "공연명 요소의 `font-weight` 가 500 이다" |

설정을 검사하면 **설정이 맞다는 것만** 확인한다. 컴포넌트가 그 설정을 실제로 쓰는지,
다른 스타일이 덮어쓰지 않는지는 아무도 보지 않는다. 실사용에서 설정 대조만으로 3라운드
동안 배지 모서리·카드 구분선·보조 텍스트 색 결함을 모두 놓쳤고, 렌더 기반으로 바꾸자
회귀를 자동으로 잡았다.

---

## 3. 구현이 아니라 동작을 쓴다

시나리오는 **무엇이 일어나는가**를 쓴다. **어떻게 구현하는가**는 Phase 3의 몫이다.

```
❌ When  StoreRepository.find_by_supervisor() 를 호출한다
✅ When  S가 "강남"으로 검색한다

❌ Then  SQL 쿼리에 WHERE supervisor_id = ? 가 포함된다
✅ Then  결과에 담당하지 않는 매장이 없다
```

구현을 시나리오에 박으면 리팩토링할 때마다 테스트가 깨진다.
단, **Given에는 구현 세부가 들어갈 수 있다** — 테스트가 상태를 만들어야 하기 때문이다.

---

## 4. 시나리오 타입

| type | 무엇 | 최소 개수 |
|---|---|---|
| `happy` | 정상 경로 | 1 |
| `error` | 실패·거부·예외 | 1 |
| `boundary` | 경계값 (0건, 최대 길이, 첫/마지막 페이지) | 0 |
| `regression` | 기존 동작이 깨지지 않음 | 0 |

`happy` 와 `error` 는 필수다. 오류 경로가 없는 기능은 대개 시나리오를 덜 생각한 것이다.

---

## 5. 하나의 시나리오는 하나의 관심사

```
❌  SC-01  검색이 동작하고 권한도 확인되며 페이지네이션도 된다

✅  SC-01  담당 매장이 검색된다
    SC-02  담당하지 않는 매장은 결과에 없다
    SC-03  결과가 20건을 넘으면 페이지로 나뉜다
```

시나리오 제목에 "그리고"가 들어가면 나눠야 한다는 신호다.

---

## 6. 필수 메타데이터

각 시나리오에 반드시 단다.

```markdown
covers: <acceptance_criteria 중 이 시나리오가 검증하는 것>
flow:   <PLAN_<ID>.json 의 design.flows[].id>
```

- `covers` 없는 시나리오 → 이 태스크에 왜 필요한지 설명할 수 없다. 지우거나 근거를 찾는다
- `flow` 없는 시나리오 → Plan에 없는 동작을 검증하고 있다. Plan을 고치거나 시나리오를 뺀다

---

## 7. ID 규칙

```
SC-01, SC-02, ...      태스크 안에서 유일. 2자리 0채움
```

시나리오를 삭제해도 **번호를 재사용하지 않는다.** 체크포인트와 검증 리포트가
번호로 시나리오를 가리키므로, 재사용하면 이력이 뒤섞인다.

---

## 8. 자주 나오는 실수

**Given에 When이 섞임**
```
❌ Given  사용자가 로그인하고 검색 페이지로 이동한다
✅ Given  사용자가 로그인되어 있다
   And    검색 페이지가 열려 있다
```
Given은 상태지 행위가 아니다.

**Then에 새로운 When이 숨음**
```
❌ Then  결과가 표시되고, 첫 항목을 클릭하면 상세로 이동한다
```
"클릭하면"은 새 When이다. 별도 시나리오로 뺀다.

**부정형 Then의 범위가 모호함**
```
❌ Then  오류가 발생하지 않는다
✅ Then  200이 반환된다
```
"오류가 없다"는 무엇이든 통과시킨다.
