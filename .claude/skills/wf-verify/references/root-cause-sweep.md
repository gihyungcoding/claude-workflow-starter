# 뿌리 원인 스윕 — FAIL 한 번에 같은 뿌리를 다 드러낸다

`wf-verify` Step 5·7 과 `wf-develop`·`wf-scenario` 의 Phase 4 롤백 재진입에서 참조한다.

## 왜 필요한가

Phase 4 가 FAIL 을 내면 Phase 3(또는 2a)으로 돌아가고, 고친 뒤 다시 검증하면 **같은 뿌리의
다른 입력**이 또 나온다. 되돌아갈 때마다 독립검증 · HITL · Red · Green · 리뷰를 다시 돈다.

| 태스크 | 증상이 나온 순서 | 뿌리 |
|---|---|---|
| TASK-009 | ① 소문자화로 길이가 늘어나는 이메일 → 409 오보 ② name 의 NUL 문자 → 409 오보 | 모든 `DataIntegrityViolationException` 을 UNIQUE 위반으로 취급하는 catch |
| TASK-004 | 좌석 상한 우회 → 길이 초과 · null 원소 → 소수 절삭 | 서비스 계층의 수동 검증에 새 필드·새 경로가 빠짐 |
| TASK-003 | 폰트 굵기 → 배지 radius → 구분선 → lineHeight … | 설정 객체 값이 렌더 결과에 반영되는지를 설계하지 않음 |

회고와 VERIFY 가 세 태스크 모두 뿌리가 같았다고 적었다(TASK-009 는 2차 판정이 "같은 뿌리의
결함"이라고 썼다). 증상 하나씩 고쳐 돌려보내서 라운드가 늘었다. 첫 라운드에 뿌리를 *미리*
알 수 있었는지는 사후 기록으로 확인할 수 없다 — 이 문서는 그것을 시도하게 만드는 장치이고,
효과는 다음 태스크들에서 `later` 가 얼마나 나오는지로 본다.

## 규칙 셋

1. **첫 FAIL 에서 리뷰어가 뿌리와 변종을 적는다.** 결함마다 뿌리를 한 문장으로 쓰고, 같은
   뿌리에서 나올 법한 다른 입력(변종)을 **프로브로 재현해 본다.**
2. **Phase 3 은 뿌리를 고친다.** 증상 하나가 아니라 뿌리를, 그리고 **공통 지점에서**
   (→ 「뿌리를 고친다는 것」). 재현된 변종마다 테스트를 먼저 실패시킨 뒤 고친다(Red → Green).
   **`not_probed` 변종도 테스트를 쓴다** — 테스트가 프로브다
3. **재검증은 이전 기록을 이어받는다.** 지난 `root_causes` 를 그대로 받아 변종이 모두 해소됐는지
   본다. 새 결함이 기존 뿌리에 속하면 새 뿌리를 만들지 않고 **같은 뿌리에 `origin: "later"` 로
   덧붙인다** — 첫 라운드의 스윕이 놓친 것이라는 기록이다.

## 기록 형식

`VERIFY_<ID>.json` 최상위에 둔다. `code_review` 안이 아니다 — 그쪽은 태스크마다 모양이 달라서
기계가 읽을 수 없었다.

```jsonc
"root_causes": [
  {
    "id": "RC-1",
    "summary": "DataIntegrityViolationException 을 전부 UNIQUE 위반으로 취급하는 catch",
    "found_in_round": 1,
    "variants": [
      { "case": "소문자화로 길이가 늘어나는 이메일", "origin": "found",
        "probe": "reproduced", "resolved": true, "evidence": "AuthServiceTest.longEmail" },
      { "case": "name 에 NUL 문자", "origin": "predicted",
        "probe": "reproduced", "resolved": true, "evidence": "AuthServiceTest.nulName" },
      { "case": "name 이 컬럼 길이를 넘는다", "origin": "predicted",
        "probe": "not_reproduced" }
    ]
  }
]
```

| 필드 | 값 |
|---|---|
| `origin` | `found` 리뷰어가 보고한 결함 · `predicted` 같은 뿌리라 있을 법해서 첫 라운드에 미리 적음 · `later` 이후 라운드에서 뒤늦게 나옴 |
| `probe` | `reproduced` 재현함 · `not_reproduced` 시도했으나 재현 안 됨 · `not_probed` 못 함 (`reason` 필수) |
| `resolved` | 고쳤으면 `true` + `evidence`(그것을 막는 테스트). FAIL 이 아닌 판정에서 `reproduced` 변종은 반드시 `true` — 아래 「범위」로 넘긴 것만 예외 |
| `scope` | `diff` 이 변경이 만들었거나 완료 조건을 깬다(적지 않으면 이것) · `pre_existing` 기준 브랜치에서도 재현된다 · `hardening` 어느 완료 조건에도 없는 불변식 강화 |
| `scope_evidence` | `diff` 가 아니면 필수 — `pre_existing` 은 기준 브랜치에서 재현한 방법, `hardening` 은 어느 완료 조건에도 없는 이유 |
| `deferred_to` · `deferred_reason` | `diff` 가 아닌 재현 변종을 넘길 후속 태스크(tasks.json 에 실제로 있어야 한다)와 이 태스크에서 고치지 않는 이유 |

변종이 정말 없으면 `variants: []` 와 함께 `no_variants_reason` 에 **무엇을 검토했고 왜 없는지**
쓴다 (예: "이 catch 가 있는 진입점이 이 하나뿐임을 Grep 으로 확인").

**라운드를 넘길 때는 이전 항목을 그대로 옮겨 적는다.** 해소했어도 지우지 않고 `resolved` 로
남긴다. 문구를 고쳐 쓰면 `check_root_causes.py` 가 지운 것으로 읽는다.

## 범위 — 이 변경이 만든 것만 FAIL 이다

리뷰어는 넓은 불변식(「모든 오류 응답이 우리 형식이다」)을 기준으로 찌를 수 있다. 맞는 말이지만 공격면이 넓은 불변식은
찌를 때마다 새 변종이 나와 **수렴하지 않는다.** ssirleague TASK-004(이미지 빌드·SPA 폴백)는 그렇게 Phase 4 를 4라운드 돌았다 —
405 → 415·400 → Range 416·컨테이너 수준 400 → 커밋된 응답. 그중 상당수는 이 변경 전부터 있던 것이었고, 2라운드에 사람이
「후속 태스크로 분리」를 골랐는데 게이트가 막았다.

변종마다 `scope` 를 적는다.

| scope | 판정 | 무엇으로 정하나 |
|---|---|---|
| `diff` | FAIL — 이 태스크에서 고친다 | 이 diff 가 연 경로·바꾼 코드에서 나거나, 완료 조건·시나리오를 깬다 |
| `pre_existing` | 넘길 수 있다 | **기준 브랜치에서 같은 입력으로 재현된다** — 프로브를 기준 브랜치에서도 돌려 `scope_evidence` 에 적는다 |
| `hardening` | 넘길 수 있다 | 완료 조건·시나리오·conventions·ADR 어디에도 그 약속이 없다 |

**이 diff 가 새로 연 경로에서 나는 것은 원래 있던 처리기 탓이어도 `diff` 다** — 이 변경 전에는 사용자가 닿을 수 없었다.
TASK-004 의 정적 파일 Range 416 이 그렇다. 판단이 갈리면 `diff` 로 둔다.

`diff` 가 아닌 재현 변종이 남았을 때:

1. 사람에게 묻는다(HITL#3) — 지금 고친다 / 후속 태스크로 넘긴다
2. 넘기면 후속 태스크를 **먼저 만든다**(`/wf-task-new`). 적어만 둔 이관은 아무도 하지 않는다
3. 변종에 `deferred_to`·`deferred_reason`·`scope_evidence`, 판정은 **WARN**(사람이 넘김을 본다)

`check_root_causes.py` 는 `diff` 넘김 · 없는 태스크로 넘김 · 근거 없는 넘김 · 넘김이 있는데 PASS 를 막는다.
**범위 판단이 맞는지는 기계가 모른다** — 그래서 넘긴 수를 따로 세어 HITL#3 에 보인다. 넘긴 변종은 `/wf-retro` 가
실패 유형 카탈로그(`docs/architecture/failure-modes.md`) 후보로 모은다 — 다음 태스크의 2a 가 처음부터 덮게 하는 길이다.

## 변종을 찾는 질문

뿌리를 적은 뒤 아래를 하나씩 물어 후보를 만든다. 후보가 없으면 없다고 적는다.

- **같은 코드 경로를 지나는 다른 입력은?** 한 필드가 문제였다면 같은 DTO 의 다른 필드, 같은
  타입의 입력 전부 (예: 문자열 필드마다 길이·NUL·공백·유니코드)
- **같은 패턴이 다른 곳에도 있는가?** Grep 으로 같은 catch · 같은 변환 · 같은 분기를 찾는다
- **같은 예외를 일으키는 다른 원인은?** 넓게 잡은 catch 는 원인이 여럿이다
- **같은 가정이 깨지는 다른 환경은?** 테스트 DB 와 운영 DB 의 차이(H2 ↔ PostgreSQL), 설정값 조합
- **이 수정이 새로 만들 부작용은?** (`code-review-rounds.md` §2)
- **실패 유형 카탈로그에 이 노출면의 칸이 있는가?** `docs/architecture/failure-modes.md` 에서 이 태스크가 연 노출면의 행을 읽고
  2a 가 `n/a` 로 닫은 칸도 다시 본다 — 그 사유가 틀렸으면 그것이 변종이다

## 프로브 규칙

프로브는 **재현 시도**다. 저장소를 바꾸지 않는다.

- 임시 테스트·스크립트는 저장소 밖(시스템 임시 디렉터리)에 둔다. 저장소 안에 파일을 만들지 않는다
- 운영 DB · 외부 서비스에 쓰지 않는다. 로컬 · 인메모리 · 테스트 컨테이너만 쓴다
- 환경이 없어 못 하면(예: Docker 꺼짐) `not_probed` + `reason` 으로 정직하게 적는다.
  `not_reproduced` 로 적으면 "시도했는데 안 됐다"는 거짓 기록이 된다
- **판단으로 건너뛰지 않는다.** "영향이 없을 것" 은 `not_probed` 의 사유가 아니다 — 그 판단이
  맞다면 프로브가 보여준다. TASK-009 3차가 "password 의 짝 없는 서로게이트" 를 "getBytes 변환이
  해시·매칭에서 같아 영향 없다고 판단" 하고 넘겼고, 그것이 4차 FAIL(로그인 비밀번호 200)이었다
- `not_probed` 로 넘긴 변종은 **다음 라운드에 반드시 프로브되어 있어야 한다.** Phase 3 의
  테스트가 그 프로브다. 재현되지 않았으면 `not_reproduced` 와 그것을 보인 테스트(`evidence`)

## 뿌리를 고친다는 것 — 공통 지점에서

같은 뿌리의 변종이 둘 이상이면 **공통 지점**(검증기 · 필터 · 역직렬화 · 공용 메서드)에서 한 번에
막는다. 필드·호출부마다 따로 고치면 빠뜨린 한 곳이 다음 FAIL 이 된다.

TASK-009 가 그랬다. 짝 없는 서로게이트 검사를 DTO 필드마다 `@Pattern` 으로 붙였고
(`SignUpRequest` 의 이메일 · 비밀번호, `LoginRequest` 의 이메일), `LoginRequest.password` 에 빠졌다.
그것이 4차 결함이다. 뿌리 요약도 라운드마다 넓어졌다 — "DB 가 무손실로 저장하지 못하는 문자열"
→ "… 또는 비교 단계에서 다른 값으로 치환되는 문자열". 실제 뿌리는 **문자열 입력이 경계에서
한 번도 검증되지 않는다**였고, 그것은 한 곳에서 막을 수 있었다.

- 공통 지점이 있으면 거기서 고치고, 기존의 위치별 수정은 걷어낸다
- 공통 지점이 정말 없어 위치마다 고쳐야 하면, 그 뿌리가 걸리는 **모든 위치를 Grep 으로
  열거**해 `DEV_<ID>.json` 의 `rollback_fixes[].sites` 에 남긴다. 열거가 빠짐없는지가 핵심이다
- 재검증 리뷰어는 수정 위치를 본다. 위치별 수정이면 같은 Grep 으로 빠진 위치를 찾는다

## 검사

```bash
python3 scripts/check_root_causes.py --task-id TASK-001
```

| 막는 것 | 방식 |
|---|---|
| 뿌리 없는 FAIL | FAIL 이면 `root_causes` 가 비어 있지 않아야 한다 |
| 재현된 변종을 남긴 채 통과 | FAIL 이 아닌 판정에서 `reproduced` 변종은 `resolved: true` + `evidence` |
| 불리한 항목 삭제 | 이전에 커밋된 VERIFY 의 뿌리·변종이 지금 파일에 있어야 한다 (git 이력 대조) |
| 프로브 미루기 | 이전 라운드에 `not_probed` 였던 변종은 이번 라운드에 프로브되어 있다. `not_reproduced` 면 `evidence` 필수. 이전 라운드 = 그 VERIFY 이후 이 브랜치에서 소스가 바뀐 경우 (기준 브랜치 병합분 제외) |

**못 막는 것: 기록의 질과 수정 위치.** 요약이 그럴듯한지, 변종 후보가 충분한지, 프로브를 실제로
돌렸는지, 수정이 공통 지점에 있는지는 알 수 없다. 형식만 채워도 통과한다. 그래서 `not_probed` 와
`later` 를 숨기지 않고 세어 보여주고, 수정 위치는 리뷰어가 본다.

## 사람에게 보이는 것

- **FAIL 롤백 요약** — 뿌리 N건 · 변종 M건(재현 K건 · 미확인 J건). 사람은 증상 목록이 아니라
  이 숫자로 "이 롤백이 한 번에 끝날 만한가"를 본다
- **Phase 5 회고** — `later` 가 있으면 첫 라운드 스윕이 놓친 것이다. 어떤 질문이 빠졌는지가
  개선 재료가 된다
