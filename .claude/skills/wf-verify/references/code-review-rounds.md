# 코드 리뷰 — 재시도 라운드를 줄이는 호출법

`wf-verify` Step 5 에서 참조한다. `code-reviewer` 를 **두 번째 이후** 부를 때의 규칙이다.

실사용에서 Phase 4 가 FAIL 을 내고 Phase 3 으로 돌아갔다가 다시 검증하는 일이 태스크당
평균 두 번이었다. 그 재시도의 대부분은 **같은 부류의 새 결함이 하나씩 나와서**였다.

---

## 1. 재호출할 때는 같은 부류를 전수 확인하게 한다

이전 라운드에서 결함을 지적했으면, 재호출 프롬프트에 **이전 `root_causes` 를 그대로 넘기고**
(→ `root-cause-sweep.md`) 변종이 모두 해소됐는지, 같은 뿌리의 새 결함이 없는지 보게 한다.
`root_causes` 가 없는 오래된 VERIFY 라면 **결함의 카테고리를 지목해** 잔여 사례를 전부
찾게 한다.

```
이전 라운드에서 "title·venue 길이 상한 미검증" 이 지적됐고 수정됐습니다.
같은 카테고리 — 문자열 필드의 길이 검증 — 의 잔여 사례를 **전수** 확인해주세요.
수정된 한 곳이 아니라 요청 DTO 의 모든 문자열 필드를 봐야 합니다.
```

지목하지 않으면 리뷰어는 "수정된 곳이 고쳐졌는가" 만 보고, 같은 구조의 다른 곳은 다음
라운드에서야 발견된다. 3라운드까지 간 태스크가 이 패턴이었다.

## 2. 롤백 후 수정 커밋은 반드시 다시 리뷰한다

Phase 3 으로 돌아가 결함을 고친 뒤 Phase 4 에 다시 들어오면, **그 수정 커밋을 리뷰어로
최소 1회 다시 검토한다.** 결함을 고치는 패치 자체가 새 결함을 만들 수 있다.

실제로 오류 표시를 추가하는 수정이 상태 초기화를 빠뜨려 새 결함이 됐고, 2차 재검토가
그것을 잡았다. "고쳤다고 했으니 통과"로 두면 그 결함이 승인된 코드에 남는다.

재검토 프롬프트에는 **무엇을 고쳤는지**(커밋 범위)를 주고, 그 변경이 만들 수 있는
부작용을 보게 한다.

```
비교 기준: git diff <롤백 직전 커밋>...HEAD   ← 이번 수정분만
이 수정이 새로 만들 수 있는 결함(초기화 누락, 상태 불일치, 다른 호출자 영향)을 봐주세요.
```

## 3. 기록

`VERIFY_<ID>.json` 의 `code_review.rounds` 에 라운드마다 한 줄을 남긴다.

```jsonc
"code_review": {
  "rounds": [
    { "n": 1, "scope": "전체", "findings": 2 },
    { "n": 2, "scope": "수정 커밋 a1b2c3d..HEAD · 같은 카테고리 전수", "findings": 1 }
  ]
}
```
