# 화면 확인 — Frontend 태스크의 증거 수집

`wf-verify` Step 2.5 에서 참조한다. Frontend 태스크가 아니면 읽지 않는다.

시안이 없는 프로젝트가 많다. 그림과 비교하는 것보다 **실제로 그 상태가 되는지 보는 편**이
확실하다. feature 문서 §5 의 상태 목록이 기준이다.

```bash
jq -r '.source_refs.source_file' workflow_design/04_plan/PLAN_<ID>.json
```

앱을 띄운다 — 프로젝트에 맞는 방법을 쓴다 (`run` 스킬이 대부분 처리한다).
웹이면 브라우저 도구로, iOS 앱이면 시뮬레이터로 조작한다.

## 상태를 실제로 만들어 본다

기본 상태만 보고 끝내지 않는다. **기본 화면은 대부분 그냥 나온다** — 결함은 나머지에 있다.

| 상태 | 어떻게 만드나 |
|---|---|
| 기본 | 데이터가 있는 상태로 접속 |
| 빈 목록 | 데이터를 비우거나 검색어를 없는 값으로 |
| 로딩 | 느린 응답을 흉내내거나 로딩 순간 포착 |
| 오류 | 서버를 끄거나 잘못된 요청 |
| 권한 없음 | 권한 없는 계정으로 |

## 기록

```jsonc
"screens": [
  { "name": "할 일 목록", "state": "기본", "verdict": "PASS",
    "evidence": "카드 3건, 제목·마감일·체크박스 모두 표시" },
  { "name": "할 일 목록", "state": "빈 목록", "verdict": "PASS",
    "evidence": "\"아직 할 일이 없습니다\" + [새로 만들기] 확인" },
  { "name": "할 일 목록", "state": "오류", "verdict": "WARN",
    "evidence": "서버 중단 시 빈 화면. 명세에는 [다시 시도] 버튼이 있어야 함" }
]
```

스크린샷은 HITL 리포트 Artifact 에 첨부한다.

## 못 봤을 때

**앱을 띄울 수 없으면** (환경 미비, 빌드 실패, 외부 의존) 그 사실을 적고 `WARN` 으로 둔다.
확인하지 않은 것을 PASS 로 쓰지 않는다 — `references/evidence-integrity.md` 와 같은 원칙이다.

명세에 있는 상태가 실제로 안 나오면 `status: FAIL` 이다. 완료 조건 미충족이다.
