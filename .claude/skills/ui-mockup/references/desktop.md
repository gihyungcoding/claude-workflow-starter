# 데스크톱 — 모바일을 늘리지 않고 따로 짠다

**데스크톱은 같은 일을 더 넓은 화면에서 하는 것이 아니라, 일하는 방식이 다르다.** 마우스·키보드가 있고, 여러 것을
나란히 보고 비교하며, 한 번 앉아서 여러 건을 처리한다. 모바일의 "한 화면에 한 가지 일"은 데스크톱에서
**"한 화면에 한 가지 목적 + 그 목적에 필요한 맥락을 나란히"** 가 된다.

## 1. 배치 계획 — 빌드 전에 쓴다 (`OUT/layout.md`)

모바일 화면 목록이 정해진 뒤, 데스크톱 화면을 **따로** 정한다.

1. **묶기**: 모바일 화면 여러 장이 데스크톱 한 화면이 되는 경우를 찾는다. 판단 질문은 "사용자가 이 화면들을
   오가며 같은 일을 하는가?" — 목록 → 상세 → 확정처럼 왔다 갔다 하는 묶음은 데스크톱 한 화면(목록·상세 나란히 +
   확정은 대화상자나 측면 패널)이 된다. 모든 모바일 화면은 정확히 하나의 데스크톱 화면에 속한다.
2. **도메인에서 구조를 끌어낸다**: 이 제품의 대상이 시간·상태·사람 중 무엇을 따라 쌓이는지 본다.
   날짜에 몰리고 겹치면 달력, 정해진 순서의 상태를 거치면 보드, 수십 명·수십 건을 기준을 바꿔 훑으면 표 + 필터,
   하나를 깊게 보며 고치면 측면 패널. **이 앱에서만 성립하는 사실이 있으면 구조에 반영한다**
   (예: 특정 요일·시간대에 몰린다면 그 칸을 넓힌다). 반영한 사실과 이유를 `layout.md` 에 적는다.
3. **화면마다 ASCII 배치**를 그린다. 무엇이 어디에 얼마나 크게 놓이는지만 — 색은 그리지 않는다.
   가장 큰 면적은 그 화면 목적의 주인공. 비교하고 싶은 대안이 있으면 둘 그려 보고 고른 이유를 한 줄.
4. **검토**: 각 데스크톱 화면에 대해 "모바일 화면을 가운데 정렬해 늘린 것과 무엇이 다른가?"에 한 줄로 답한다.
   답이 "폭만 넓다"면 다시 짠다. **다른 점은 배치이지 내용이 아니다** — 넓은 자리를 채우려고 모바일에 없는 구역을 더하지 않는다.
   그 내용이 쓸모 있으면 모바일에도 넣는다(시험 2: 대회 규칙 설명이 데스크톱에만 있었다). 정말 데스크톱만의 것(단축키 안내 등)이면
   그 구역에 `data-desktop-only="이유"` — 정적 검사가 위반 대신 경고로 보인다.

```markdown
## 데스크톱 화면
| id | 묶는 모바일 화면 | 패턴 | 주인공 | 이 앱의 사실 |
|---|---|---|---|---|
| d-plans | plans, plan-detail, plan-confirm | 목록·상세 나란히 + 확정 대화상자 | 선택한 항목의 진행 | 대부분 3~6명 단위 |

### d-plans
┌──────┬────────────────┬──────────────────────────┐
│ 내비 │ 목록 (상태 필터) │ 상세: 진행 · 응답 표 · 확정 │
└──────┴────────────────┴──────────────────────────┘
모바일을 늘린 것과 다른 점: 다음 항목으로 넘어가도 목록이 그대로 보인다
```

## 2. 패턴 — 판단 질문에 "예"일 때만

| 패턴 | 판단 질문 | 부품 (`kit/DESKTOP.md`) |
|---|---|---|
| **사이드 내비 골격** | 앱 안의 목적지가 3곳 이상인가? (모바일 탭바의 데스크톱 짝) | `shell` · `sidenav` · `nav` |
| **보조 열** | 본문을 보면서 계속 곁에 둘 요약·다음 할 일이 있는가? 본문이 넓어야 하는 화면(달력·보드·표)이면 보조 열을 두지 않고 그 아래로 내린다 | `main has-aside` · `aside` |
| **현황 홈** | 홈에서 그 사람이 알고 싶은 것이 3가지 이상이고 모양이 다른가(숫자·목록·날짜)? | `d-head` + `stats` + `grid-2` 블록 |
| **목록·상세 나란히** | 목록에서 하나를 골라 보고, 다음 것으로 넘어가는 일이 잦은가? | `split` · `split-list` · `split-detail` |
| **상태 보드** | 대상이 정해진 순서의 상태를 거쳐 가고, 상태마다 몇 건인지가 중요한가? 열 = 상태(순서대로) | `board` · `board-col` · `card` |
| **월 달력 격자** | 날짜에 따라 몰림·겹침을 봐야 하는가? 겹친 날은 표시, 특정 요일이 중요하면 그 칸을 넓힌다 | `cal` · `cal-grid` · `cal-ev` · `is-weekend-wide` |
| **표 + 늘 보이는 필터** | 30건이 넘는 대상을 기준을 바꿔 훑거나, 여러 개를 한꺼번에 처리하는가? | `with-filters` · `filters` · `dtable` · `bulkbar` |
| **측면 패널** | 고치는 동안 원래 목록·맥락을 계속 봐야 하는가? 입력이 많으면 별도 화면 | `panel` (보조 열 자리) |
| **대화상자** | 되돌릴 수 없는 확인, 짧은 선택(모바일 시트의 짝) | `dim` · `dialog` |
| **단독 페이지** | 앱을 쓰지 않는 사람이 링크로 여는가? → 앱 내비 없이 가운데 한 열 | `body.desk.standalone` · `sheet-page` |

## 3. 데스크톱 규칙

- 페이지 머리는 두 열 위 전체 폭, 폭은 정해진 것만, 상태 화면은 기본 화면 복사, 버튼은 한 줄·묶음은 `btn-row` — `kit/DESKTOP.md` 「뼈대」「버튼」

- 첫 화면(1280×800, 스크롤 전)에 그 화면의 주인공이 다 보인다. 위쪽을 머리글·배너가 차지하지 않는다.
- 주 행동은 페이지 머리 오른쪽(`d-actions`) 또는 패널·대화상자 바닥. 화면 하단 고정 버튼은 쓰지 않는다.
- 누르는 것은 hover 상태가 있고, 최소 높이 36px(본문 안 버튼)·44px(행).
- 한 줄 글은 80자를 넘기지 않는다 — 넓은 칸에는 글 대신 구조(열·표·달력)를 둔다.
- 모바일과 같은 사실 표·배지 표·말투를 쓴다. 데스크톱이라고 다른 이름으로 부르지 않는다.
