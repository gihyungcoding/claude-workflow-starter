# 문서 지도 — 새 기능은 어떻게 시작되는가

아이디어가 코드가 되기까지 거치는 문서와 절차를 한 장으로 정리한다.

> 이 문서가 존재하는 이유: 원본 저장소에는 "MR 게이트를 통과하는 법"과 "Phase 1 이후 개발
> 워크플로우"는 문서화되어 있었지만 **그 사이가 비어 있었다.** 기능을 어디서 시작해서
> 어떻게 태스크가 되는지를 아는 사람만 알았다.

---

## 두 계층

```
┌─ Foundation ── 프로젝트 수준. 자주 바뀌지 않는다 ──────────┐
│                                                            │
│   product.md  ──►  architecture.md  ──►  ADR-NNNN.md       │
│   무엇을 왜          어떻게 구성            왜 이렇게 결정   │
│       │                   │                   ▲            │
│       ▼                   │                   │            │
│   features/*.md ──────────┘                   │            │
│   이번에 만들 것                               │            │
│       │  §1-2 태스크 분리 표                   │            │
│       ▼                                       │            │
│   tasks.json                                  │            │
└───────────┬───────────────────────────────────┼────────────┘
            │ 태스크 1건씩                       │
            ▼                                   │
┌─ Workflow ── 태스크마다 반복 ─────────────────┼───────────┐
│   Phase 1 ─► 2a ─► 2b ─► 3 ─► 4 ─► 5          │           │
│   Plan   Scenario Red  Green Verify Reflect ──┘           │
│                                    ADR 신규/갱신 제안      │
└────────────────────────────────────────────────────────────┘
```

Foundation은 **간헐적으로** 갱신되고, Workflow는 **태스크마다** 돈다.
Phase 5 회고가 Foundation을 되먹이는 것이 이 구조의 핵심이다 — 그 고리가 없으면
아키텍처 문서는 반년 뒤 아무도 믿지 않는 문서가 된다.

## 상황별로 무엇을 하나

| 지금 상황 | 할 일 |
|---|---|
| 프로젝트를 막 시작했다 | `/wf-init` — product → architecture → 첫 ADR |
| 새 기능을 만들고 싶다 | `/wf-feature <이름>` → 요구사항 문서 작성 |
| 요구사항 문서가 준비됐다 | `/wf-tasks-from-doc docs/product/features/<이름>.md` |
| 태스크 하나만 급히 필요하다 | `/wf-task-new "설명"` |
| 기술 선택을 했다 | `/wf-adr "<결정 요약>"` |
| 태스크를 개발하겠다 | `/wf-start TASK-001` |
| 개발이 끝나 머지하겠다 | `/wf-ship` |
| 하던 걸 이어가겠다 | `/wf-resume` |
| 지금 뭐가 돌아가는지 보겠다 | `/wf-status` |

## 문서별 역할

| 문서 | 답하는 질문 | 누가 읽나 | 언제 바뀌나 |
|---|---|---|---|
| `product/product.md` | 무엇을 왜 만드는가. 누구를 위한 것인가 | 사람, 태스크 생성 | 방향이 바뀔 때 |
| `product/features/*.md` | 이번에 무엇을 만드는가. **어떤 태스크로 쪼개지는가** | 사람, 태스크 추출 | 기능마다 새로 |
| `architecture/architecture.md` | 시스템이 어떻게 구성되는가 | 사람, **Phase 1** | 구조가 바뀔 때 |
| `architecture/constraints.yaml` | 무엇을 어기면 안 되는가 (기계 검사용) | **Phase 4 스크립트** | 제약이 생길 때 |
| `decisions/ADR-*.md` | 왜 이 기술·패턴을 골랐는가 | 사람, **Phase 1** | 결정할 때마다 (추가만) |
| `workflow/*.md` | 워크플로우 자체의 규격 | 각 Phase 스킬 | 워크플로우를 고칠 때 |
| `workflow/first-run-notes-template.md` | 첫 완주 때 마찰을 기록하는 양식 | 처음 쓰는 사람 | — |

## 요구사항 문서의 핵심 — §1-2 태스크 분리

`features/_TEMPLATE.md` 의 `## 1-2. 태스크 분리` 표가 **이 문서 체계에서 가장 중요한 부분**이다.

화면이 있는 기능은 **`## 2. 화면 설계` 를 §3 API 보다 먼저 쓴다.** 특히 `2-2 참조` —
비슷한 상용 서비스를 하나 열고 대조하는 절 — 를 건너뛰지 않는다. 도메인을 모르면
무엇이 빠졌는지 모르고, 그 누락이 데이터 모델까지 그대로 간다.

문서 저자가 직접 Task A/B/C로 쪼개고, 각각의 범위·산출물·"포함하지 않음"·선행 조건을 적는다.
`/wf-tasks-from-doc` 는 그 표를 읽어 `tasks.json` 을 만든다 — **문서 전체를 해석해 태스크를
상상하지 않는다.**

이렇게 하는 이유:

- 사람이 판단한 분해가 LLM이 추론한 분해보다 안정적이다
- 표가 곧 명세라서 나중에 "왜 이렇게 쪼갰지?"를 되짚을 수 있다
- 문서와 태스크가 1:1로 대응해 추적이 끊기지 않는다

§1-2가 없는 문서로 추출을 시도하면 **거부하고 태스크 분리를 먼저 하자고 제안한다.**

## 작성 규약

| 항목 | 규칙 |
|---|---|
| 파일명 | 케밥케이스 (`member-learning-history.md`). 스네이크·카멜 금지 — 훅이 검사한다 |
| 범위 | `## 범위 외` 섹션을 반드시 둔다. 무엇을 안 하는지가 무엇을 하는지만큼 중요하다 |
| 코드 참조 | 실제 파일 경로·클래스·함수·엔드포인트를 **그대로 인용**한다. 추상적으로 쓰면 태스크 추출이 코드를 찾지 못한다 |
| 다이어그램 | 문서 안에서는 ASCII 박스. grep·LLM 친화적이어야 한다. mermaid 는 사람이 볼 Artifact 리포트에서만 |
| 완료 조건 | Task별 체크박스로. 그대로 `acceptance_criteria` 가 된다 |
| 화면 | **시안이 없어도 된다.** UI 라이브러리를 정하고, 상태별로 무엇이 보이는지 글로 적는다. 시안이 있으면 링크만 걸고 이미지는 복사하지 않는다 |
| 날짜 | 확정·갱신 표시를 인라인으로 남긴다 (`[확정 2026-09-01]`) |
| 인덱스 | `features/README.md` 와 `decisions/README.md` 는 `scripts/rebuild_doc_index.py` 가 생성한다. 직접 편집하지 않는다 |

## 태스크가 끝난 뒤

Phase 5(회고)까지 마치면 `/wf-ship` 으로 머지를 준비한다. Ship 은 PR 을 만들 뿐
**머지하지 않는다** — 리뷰를 거쳐 사람이 병합한다.

Ship 이 확인하는 것 중 하나가 **신선도**다. Phase 4에서 사람이 승인한 커밋과 현재 코드를
대조해, 승인 이후 소스가 바뀌었으면 PR 생성을 막고 재검증을 요구한다. 승인이란 특정
시점의 코드에 대한 것이지 브랜치 전체에 대한 백지 위임이 아니기 때문이다.

체크포인트나 회고 문서가 추가된 것은 소스 변경으로 보지 않는다 — 정상 흐름에서
승인 이후에도 산출물 커밋이 이어지기 때문이다.

## 화면이 있는 기능은 순서가 다르다

태스크 실행은 BE → FE 순이지만, **문서를 쓸 때는 화면을 먼저** 적는다.

```
① 화면과 상태를 적는다        (feature §5 화면 명세)
② 그 화면이 필요로 하는 데이터를 도출  →  §2 API 명세
③ 그다음 태스크를 나눈다       (§1-2)
```

화면을 모른 채 API 를 먼저 설계하면 "만들고 보니 이 필드가 없다"가 된다.
구현은 서버부터 하되, 생각은 화면부터 한다.

시안이 없어도 된다. UI 라이브러리를 정해두면 생김새는 라이브러리가 결정하고,
남는 것은 "무엇을 보여줄지"와 "어떤 상태가 있는지" — 그건 기획이지 디자인이 아니다.

## BE/FE 분리 원칙

백엔드(API)와 프론트엔드(화면)는 **항상 다른 태스크, 다른 PR**로 만든다.
프론트엔드 태스크는 `depends_on` 에 백엔드 태스크를 반드시 넣는다.

한 태스크에 묶으면 Red 테스트가 두 스택에 걸치고, Green 구현이 커지고, 검증 범위가
흐려진다. §1-2 표에서 애초에 나눠 쓴다.
